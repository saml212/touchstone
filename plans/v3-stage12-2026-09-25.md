# v3 stage 12 — database services (`kind: "db"`)

Many enterprise agents' tools read and write a database in-process (a SQL driver/ORM, or an
in-memory store loaded from JSON documents) instead of calling an HTTP API. The map already allowed a
`kind: "db"` service; before this stage such a service got a FastAPI simulator it could not use. This
stage makes a db service simulate as a materialized SQLite `state.db` the customer's real tools read
directly — no server, no port.

## Contract (general; nothing target-specific in `touchstone/`)

1. **Map** — for a db service, `base_url_env` is the env var the code reads for the database
   path/URL (else null); `base_url_default` is the literal (`:memory:`, a file path, a URL). One
   sentence in `MAP_PROMPT` says a tool reaching a database driver/ORM (or an in-memory JSON store)
   in-process is a `db` service.
2. **Simulate** (`db_sim.py`) — the provider (`DB_SIM_PROMPT`) returns ONE JSON object, either
   relational `{schema.sql, seed.json, README.md}` or document-store `{collections, README.md}`.
   Touchstone materializes `simulators/<name>/state.db`: relational executes schema.sql and inserts
   seed rows by column; a document store becomes one table per collection `(id TEXT PRIMARY KEY,
   doc TEXT)` with the JSON document in `doc`. Never an `app.py`. Fidelity is measured like HTTP
   (replay the recorded calls through the real tools, compare returned), with one-shot regeneration
   on a low score.
3. **Wiring** — the env var is the mapped `base_url_env` or a synthesized `TOUCHSTONE_DB_<NAME>`; its
   value is the abs path of state.db (or `sqlite:///<abs>` when the default is a URL). It replaces
   `http://127.0.0.1:<port>` everywhere a base url is set (replay spec, environment `base_url_envs`,
   package, solve, agent). No port is allocated; `start.sh <name>` re-materializes state.db for a sim
   with no `app.py` (`python -m touchstone.survey.db_sim <sim_dir>`) and returns.
4. **invoke.py** — `INVOKE_PROMPT` lists the db services with their env var and, for a document
   store, says to load every collection from state.db into dicts once per process, call the tool
   exactly as the code does, and write changed documents back (json.dumps, sorted keys) after each
   call.
5. **Criteria** — `capture_effect` mounts and diffs `simulators/<svc>/state.db` the same way; a
   document-store change becomes `rk.sqlite_query_equals(..., "SELECT json_extract(doc,'$.field')
   ...", ...)` per changed field, not a whole-blob check. Existing criteria rules apply unchanged.
6. **Environment** — the image carries `simulators/<name>/{schema.sql, seed.json | collections.json,
   README.md}`; state.db is rebuilt at start; the agent's env exports the db env var. Verifier
   artifacts already include the state.db.
7. **Unsupported** — a db service whose tools cannot run against SQLite is written as
   `UNSUPPORTED.md`; fidelity reports 0 with the reason and the report says so.
8. **Report** — db simulators appear with kind `db` and their fidelity like any other; an
   unsupported service shows its reason.

## What shipped

- `touchstone/survey/db_service.py` — env-var name/value + container-path helpers.
- `touchstone/survey/db_sim.py` — `DB_SIM_PROMPT`, parse, write, materialize (both shapes),
  UNSUPPORTED, `generate_db_simulator`, `python -m touchstone.survey.db_sim` CLI.
- `map.py` (prompt), `simulate.py` (dispatch + `_replay_ctx`), `fidelity.py` (materialize + replay,
  no server), `environment.py` (synth env, no port, `start.sh` db branch, kinds/db_urls),
  `package.py` (base_urls + manifest), `task_files.py` (solve + replay spec), `harbor/agent.py`
  (`setup()` db branch), `criteria.py` (doc-store json_extract + db mounts), `invoke.py` (prompt +
  db mounts), `report.py` (unsupported status).
- Also in this stage: `touchstone.capture.paused()` (suspend non-agent model/tool spans) and
  litellm capture wired into `trace()` with SDK dedupe.

Live acceptance target: `~/Pebble/Github/survey-targets/tau-bench` (retail env, document store).
